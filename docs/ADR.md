# Architecture Decision Records

## 철학
MVP 속도 최우선. 외부 의존성 최소화. 작동하는 최소 구현을 선택한다. 비즈니스 가치의 핵심(점수·추천)은 순수 함수로 분리해 테스트로 보호한다.

---

### ADR-001: Next.js 15 App Router 채택
**결정**: App Router 기반 단일 Next.js 앱. 화면과 API 라우트를 한 프로젝트에서 처리.
**이유**: 프론트(폼·결과)와 서버(YouTube 호출·키 보관)를 한 코드베이스로 묶어 MVP 개발/배포가 단순. 기존 셋업(.gitignore, npm 훅)과 일치.
**트레이드오프**: 별도 백엔드 분리의 유연성 포기. MVP 규모에선 불필요.

### ADR-002: 테스트 러너로 Vitest 채택
**결정**: 단위 테스트는 Vitest(`vitest run`)로 실행. `npm run test`에 직접 매핑.
**이유**: TS/ESM 설정 부담이 적고 순수 함수 테스트에 빠르다. Stop 훅(`npm run test`)과 호환.
**트레이드오프**: Jest 생태계 일부 도구 미사용. 핵심: 반드시 watch 금지(`vitest run`) — watch면 Stop 훅이 멈춘다.

### ADR-003: 유사 영상은 키워드 검색으로 수집
**결정**: 시드 영상의 제목/태그에서 키워드를 추출해 `search.list(q=...)`로 비슷한 영상을 찾는다.
**이유**: `search.list`의 `relatedToVideoId` 파라미터는 2023년 제거되어 응답하지 않는다. 키워드 검색이 현재 유일하게 동작하는 방식.
**트레이드오프**: "관련 영상"의 정밀도가 알고리즘 추천보다 낮을 수 있음. 키워드 선택으로 보완.

### ADR-004: 통계는 videos.list 단일 batch로 2차 조회
**결정**: `search.list`로 ID만 받고, 후보 ID들을 `videos.list?part=statistics,...`로 한 번에(최대 50개) 조회.
**이유**: `search.list`는 통계(viewCount 등)를 반환하지 않는다. 영상별 개별 호출은 quota를 50배 낭비.
**트레이드오프**: 호출이 2단계로 늘지만, quota는 1회 분석 ≈ 102 units로 저렴(일 10,000 한도 내 약 90회).

### ADR-005: 분석은 정량 지표만, LLM 미사용
**결정**: 조회수·좋아요·댓글·참여율·조회수 증가속도를 min-max 정규화 후 가중합해 점수화. 추천도 키워드 빈도+지표 비교로만 생성.
**이유**: MVP 단순성·비용·예측가능성. LLM 없이도 "더 나은 콘텐츠 비교"와 "다음 추천"이 가능.
**트레이드오프**: 콘텐츠 질·맥락의 정성 분석 불가. 비공개 지표(좋아요/댓글)는 중간값 보정으로 처리.
